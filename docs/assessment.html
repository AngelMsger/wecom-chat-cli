Assessment and scope

Checked against the public official CLI reference and smart-bot SDK on 2026-11-06. Service methods in the official CLI are dynamically discovered; documentation inspection does not prove what every tenant's gateway exposes.

Recommendation

Build this as a focused bridge and policy broker if untrusted employees need reactive conversations with agents that otherwise hold powerful tools. Transport alone is not a strong reason to maintain another CLI: the official SDK already implements it. The durable value is independently enforced admission, provenance, scoped task capabilities, independently reviewed replies, risk memory and a portable host interface.

If a host already provides equivalent bot transport, separate workers, least privilege, per-sender state and a policy-controlled reply channel, an adapter may be cheaper. Reassess the official CLI as it evolves. Official feature overlap does not by itself replace this isolation boundary.

Feasibility and evidence

  • The official Node SDK documents wss://openws.work.weixin.qq.com, subscription with Bot ID/Secret, pushed callbacks, heartbeats and replies using the callback's req_id.
  • Its connection manager serializes replies per request, waits for acknowledgements, and stops reconnecting when displaced by another subscriber. This bridge follows those semantics.
  • Its message types distinguish sender ID, group/single conversation, message ID and optional quote.
  • The official CLI reference describes dynamically discovered remote methods and gives message aibot sessions list as an example. It does not establish a persistent, isolated agent bridge. Calling this simply a "static message-list CLI" would overstate what was verified.
  • Tencent's ADP integration guide describes smart-bot single conversations and group mentions via long connection. It is not permission to observe all employee conversations.

The transport is feasible without a public inbound endpoint. Delivery during disconnection, tenant permissions, exact reply validity windows and compatibility with existing bot integrations require live testing in the target tenant. The default 120-second reply TTL is a conservative local policy, not a claim about an official server deadline. The upstream can reject a shorter window.

Safety assessment

Prompt injection detection is inherently incomplete. Obfuscated, indirect or multi-turn attacks can pass a rule or model classifier. A safe architecture must remain bounded when the model follows an attack:

  1. The privileged supervisor owns policy, secrets and worker lifecycle.
  2. Only a disposable low-privilege worker receives raw external messages.
  3. The broker exposes single-event task reads, immutable reply drafts and risk reports, never shell/file access or arbitrary recipients.
  4. Business actions needing authority must be introduced later as separately authorized narrow capabilities, outside conversational claims of identity.

Giving the same unsandboxed host agent a cautionary message is not isolation. Similarly, output secret patterns cannot protect secrets already accessible through another tool. Keep sensitive data out of the conversational worker.

Intentional product differences: explicit socket/bot/deployment flags instead of named contexts; broker-only environment credentials instead of worker login; no raw/table/projection output; no automatic runtime update checks; companion Skill is a checked-in guide, without an install/handshake command. Repository, Pages, CI and release infrastructure follow the family release pattern. The kit's HTTP retry layer does not implement WebSockets; the domain transport therefore owns subscription/reconnect, with no retry of remote writes.

Free-text bot replies require independent operator approval of the exact draft digest. Unattended sends require explicit template policy and contain only reviewed literal text, without substitutions. The bot sends in its own identity. No worker can select an event, approve itself or change a sender's access permissions.

Monitoring cost review (2026-11-10)

The family's event-driven integration guide sets the target: ordinary software owns collection, filtering, supervision and reliable handoff; idle monitoring starts no model turns. Output, durable acceptance and completed reasoning are separate stages. Prefer compact references and fetch only the context needed for an accepted task. Preserve source coverage and resolve ambiguous work instead of erasing cursors or automatically replaying actions.

Chat already had pushed intake, durable callback dedupe, bounded long polling and isolated event grants. The local gaps were replaying history on every fresh watch, returning full bodies and already assigned/closed records, and calling stdout progress delivered. The pending-reference stream fixes those defaults. The host still owns durable scheduling and actual model submission; no Grokbot integration or measured end-to-end saving is claimed.
